## §一 產品定位與端的分工（原文 §一）

LinkCard Event 生態中，**Admin App 的角色是「現場作戰終端」，不是「配置中心」**。

| 端 | 定位 | 主要使用者 | 核心職責 |
|---|---|---|---|
| **Admin Web（後台網頁版）** | 配置與管理中樞 | 主辦方 / 運營 / 客戶 | 活動建立、報名欄位、Token 規則、名單匯出、報表、權限分派 |
| **Admin App（本 repo）** | 現場執行工具 | 現場工作人員 / 攤位人員 / 督導 | 掃碼簽到、NFC 發卡、Token 增扣、即時查詢 |
| **用戶端 App / Web** | 參加者入口 | 參加者 | 報名、憑證 QR、Token 餘額、活動資訊 |

> ⚠️ 錄音明確要求：「不論是 Website 版本或 Admin App 版本，都要有呢啲相關功能」。
> 實務建議採 **「Web 全功能 + App 現場必要功能」**；App 端不做複雜規則設定，只做**高頻、單手、3 秒完成**的操作。

## §二 功能模組 A–G（原文 §二）

### 🔴 P0 — 11 月活動必須上線

#### 模組 A：QR 掃碼簽到（Check-in）

- 啟動相機即時掃碼（支援 QR；建議預留 NFC 讀取）
- 掃碼結果**三態回饋**：
  - ✅ **有效**：顯示姓名、公司、票種、報名時間、Token 餘額、簽到狀態
  - ⚠️ **重複簽到**：顯示首次簽到時間與地點，**需主管覆核才能二次放行**
  - ❌ **無效 / 未報名**：提供「現場補報名」快速通道（見模組 D）
- 簽到成功：**震動 + 音效 + 大字綠色畫面**（現場嘈雜環境必需）
- **單日 / 單場次簽到計數**即時顯示在頂部
- 簽到動作寫入**時間戳、閘口編號、操作員 ID**（稽核用）
- UI 建議：**全螢幕相機 + 底部固定「結果卡片」**，避免多層跳頁

#### 模組 B：Token / 積分管理

- **兩種入口**：① 掃 QR / 感應 NFC → 進入該用戶 Token 操作頁；② 搜尋（姓名 / 手機 / Email / 報名編號）→ 進入 Token 操作頁
- **增值（Top-up）**：預設快捷金額（+10 / +50 / +100，**數值由 Admin Web 配置**）、自訂金額、來源標記（攤位購買 / 活動獎勵 / 工作人員補發 / 贊助贈送）
- **扣減（Deduct / 兌換核銷）**：依兌換品項清單點擊扣減（如咖啡 −20、零食 −10、禮品 −50）；餘額不足時按鈕置灰並提示差額
- **交易流水**：每筆記錄時間、操作員、金額、類型、備註；用戶端與 Admin Web 同步可見
- **防呆**：扣減 / 大額增值需二次確認；可設「單筆上限」與「單日操作上限」
- 💡 商業提示：錄音傾向「**收款在外部完成、App 只做入帳**」→ 11 月版本先做記帳，**支付串接列 P2**

#### 模組 C：NFC 手帶 / 掛牌綁定（發卡）

- 簽到成功後**自動跳出「發卡」步驟**
- 寫入 / 綁定 NFC UID ↔ 用戶 Account ID
- 綁定後該 NFC 即為：① 活動入場憑證 ② Token 錢包載體 ③ **LinkCard 電子 Business Card 實體入口**
- 支援：**換卡（舊卡作廢）、補發、退卡**
- 發卡紀錄可匯出（物料盤點與成本核對）
- ⚠️ 錄音中此項負責人標記為 **@待定**，且「NFC 手帶/掛牌與電子商務卡的綁定邏輯」是**目前最大的未定義區塊**（見 §六 #4）

#### 模組 D：參加者名單與現場管理

- 名單列表：**搜尋、篩選（票種 / 簽到狀態 / 公司 / Token 餘額區間）、排序**
- 用戶詳情頁：基本資料、報名紀錄、簽到紀錄、Token 流水、綁定 NFC 編號、**所屬社團/協會**
- **現場補報名**：直接在 App 建立臨時帳戶 → 觸發同款 Email（含帳密 + QR）→ 立即發卡，流程與線上報名一致
- 匯出：CSV（簽到名單、Token 消耗報表）

### 🟡 P1 — 11 月最好有，可灰度

#### 模組 E：活動憑證 / 會員體系的 Admin 視角

- Admin App 可**代用戶出示憑證**（用戶手機沒電 / 未登入時的現場救援）
- 可檢視用戶在 LinkCard 體系的完整身分：**社團協會會員憑證 + 活動票務憑證**（多憑證並列）

#### 模組 F：工作人員帳號與權限（會議原始角色矩陣）

| 角色 | 簽到 | 發卡 | Token 增值 | Token 扣減 | 看報表 | 改規則 |
|---|:---:|:---:|:---:|:---:|:---:|:---:|
| 閘口 staff | ✅ | ❌ | ❌ | ❌ | ❌ | ❌ |
| 攤位 staff | ✅ | ❌ | ✅ | ✅ | 自己攤位 | ❌ |
| 主管 / 督導 | ✅ | ✅ | ✅ | ✅ | 全場 | ❌ |
| 主辦方 Admin | ✅ | ✅ | ✅ | ✅ | 全場 | ✅（僅 Web） |

- 支援：臨時帳號批量建立、QR 邀請加入、**即時停用**（人員離場）
- **所有操作綁定操作員 → 可追溯**

#### 模組 G：即時數據儀表板

- 報名數 / 已簽到數 / 到場率（依時段曲線）
- Token 總發放、總消耗、剩餘負債、兌換品項排行
- 各閘口 / 各攤位工作量
- 用途：主辦方現場決策與**會後結案報告**（可轉為商業賣點）

### 🟢 P2 — 11 月之後迭代

| 項目 | 說明 |
|---|---|
| **支付串接** | MPay / 信用卡直接在 App 收款並自動入 Token |
| **攤位端獨立模式（Booth Mode）** | 精簡版介面，只留「掃碼 → 扣點」，可交非技術人員 |
| **離線模式** | 場館訊號差時本地暫存、聯網後補同步（澳門展館常見痛點） |
| **推播 / 廣播** | 向已簽到用戶推送議程變更、攤位優惠 |
| **名片交換 / 社交配對** | NFC 手帶本身即 Business Card → 「碰一下交換名片」「B2B 配對推薦」 |
| **多主辦方租戶化（Multi-tenant）** | SaaS 化對外販售的前提 |

- 關鍵狀態用「**顏色 + 圖標 + 文字 + 音效**」四重冗餘

## §五 非功能需求（原文 §五）

| 類別 | 要求 |
|---|---|
| **效能** | 掃碼 → 出結果 **≤ 1.5 秒**；開場尖峰併發需壓力測試（假設 **5 分鐘內 500 人入場**） |
| **可用性** | 離線暫存隊列（至少 P1 評估）；弱網自動重試；操作可撤銷（**Undo 5 秒**） |
| **安全** | QR 需加簽名 / 一次性 token，**防止截圖轉發冒用**；Admin App 強制登入逾時；敏感個資遮罩顯示 |
| **稽核** | 全操作日誌（who / when / what / where）；**Token 增扣不可靜默修改，只能反向沖銷** |
| **多語言** | 繁體中文 / 簡體中文 / 英文 / **葡文**（澳門場景必需，容易被忽略） |
| **設備** | 中低階 Android 相容；相機對焦速度；NFC 讀寫權限；iPad / 折疊機佈局 |
| **合規** | **澳門《個人資料保護法》（第 8/2005 號法律）** — 報名個資收集需**明示同意**、Email 需含**退訂與資料用途聲明** |

## §六 待決策問題 7 項（原文 §六）

> 原文建議「本週內拍板，否則影響排期」。

| # | 問題 | 錄音中的傾向 | 原文建議 | 本輪落地狀態 |
|:---:|---|---|---|---|
| **1** | 臨時密碼是否**強制**修改？ | 傾向「不強制，方便快捷，之後可自己改」 | **不強制**，但要求隨機強密碼（非 `123456`），首次登入後以非阻斷式提示引導修改 | 待用戶拍板（後端/Web 範圍） |
| **2** | 活動憑證與社團會員憑證是否**同一套底層機制**？ | 傾向「理論上可以一樣」 | **統一抽象為 `Credential` 模型**（type: 社團會員 / 活動票務 / 電子名片），共用 QR 渲染與核驗介面 | 影響 **F-06 / W-31**（後端無 `EventCredential` model，前端僅做可選區塊） |
| **3** | Token 是**活動專屬**還是可跨活動通用？ | 未提及 | 先做「活動專屬」，但資料表預留 `scope` 欄位，為日後通用積分鋪路 | 已由 v11.3 設計承接 |
| **4** | **NFC 綁定邏輯**（負責人 @待定） | 未定義 | 🔴 **最高風險項**。需立即確認：**晶片型號/協議、是否可現場寫入、UID 是否可重複讀取、成本與到貨週期**、與電子 Business Card 的映射關係。**若來不及，11 月先用 QR 手帶降級上線** | ⚠️ **仍未有 owner**；已列施工計畫 §4.4 **P1-9** 為前置檢查 |
| **5** | Admin App 是否需**收款**功能？ | 「俾咗錢都好啦」→ 似為外部收款 | **P2**。11 月只做記帳，但 UI 預留「已收款」勾選與金額欄 | 已由 **W-22** 的「收款方式 + 參考號」欄位承接；收款方式是否含 `MPAY` **尚未驗證**（契約 §2.G **U-4**） |
| **6** | Token 活動後**餘額如何處理**？ | 未提及 | 需與主辦方約定：作廢 / 兌換截止 / 轉 LinkCard 點數 | 屬 v11.3（EXPIRY）範圍 |
| **7** | 多主辦方自助後台？ | 未提及 | 11 月由 LinkCard 團隊代配置；創業節後再做租戶化 | P2 |

> **原文特別標示「需您確認的三件事（最緊急）」**：① **NFC 綁定負責人 @待定 → 誰？**（唯一可能導致 11 月上線失敗的單點風險）② 決策 #1 / #2 是否照建議拍板；③ **11 月活動的確切日期**（用來校準 6 週排期）。

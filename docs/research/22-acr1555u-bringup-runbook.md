## 1. 硬體準備（10 分鐘）

### 1.1 讀卡機進入 BLE 可被搜尋狀態

> 以下照 `USR-ACR1555U-A1-1.07-CN.pdf` §3（官方使用者手冊原文）。

```
1. 長按「電源開關」3 秒
   → 綠燈「常亮」  = 已開機
   → 藍燈「開始閃爍」= 可被偵測 ✅

2. 若「綠燈亮但藍燈不閃」
   → 長按「模式開關」3 秒，進入藍牙模式
```

| LED 狀態                | 意思                               |
| ----------------------- | ---------------------------------- |
| 綠燈常亮 + **藍燈閃爍** | ✅ 可被搜尋，去做 §2               |
| 綠燈常亮 + **藍燈常亮** | 已被某台裝置連上（可能是你的筆電） |
| 綠燈滅                  | 沒開機或沒電                       |

> ⚠️ **「長按 MODE 4 秒可清除綁定」這個說法我查不到官方依據。**
> 它來自先前的研究文件，但 `USR V1.07` 沒有這樣寫。
> 官方的清除方式是**用 Windows 的 Configuration Tool**（手冊 §4.2），
> 或用指令 `E0 00 00 5B 00`（但手冊註明**僅限 USB 模式**）。

### 1.1b ⚠️ 如果你之前玩過 HID 模式

手冊 §4.2 附近有一句很重要的話：

> 「要切換回 NFC 讀寫器模式，請按照說明**清除綁定（配對）記錄**。」

⇒ **HID 鍵盤模式不會自己退出。** 想切回 APDU 模式，得用 Windows 工具清除配對。
**所以：先不要在平板系統設定裏把它配對成鍵盤。**

### 1.2 平板端

| 設定                   | 為什麼                                              |
| ---------------------- | --------------------------------------------------- |
| 藍牙 **開**            | 基本                                                |
| **定位（Location）開** | Android 把 BLE 掃描歸類為可能洩漏位置，關掉會掃不到 |

### 1.3 讀卡機接法

讀卡機是 **USB Type-C**，且有**內建充電電池** ⇒ 用 BLE 時不用插線，
不會吸平板電。第一次用之前建議先插 USB 充飽（`E0 00 00 52 00` 可讀電量）。

## 2. 官方 demo 驗證（1 小時）— **這是分水嶺**

目標：用**原廠自己的工具與金鑰**證明「平板 → 讀卡機 → 認證 → 讀卡」這條鏈是通的。
這一步**零風險**（金鑰是對的，不會扣錯誤額度）。

### 2.1 安裝

1. 解壓 `acssmcio-0.6.2-android21-20251203.zip`
2. `BLETest-0.6.2.apk` 傳到平板 → 安裝
3. 首次開啟允許「硬體控制」權限

> APK 就在 zip 根目錄，不用進 `BLETest/` 找。
> `scripts/mifare.txt` 可載入當 APDU 範例。

### 2.2 連線與認證

| 步驟           | 預期結果                            |
| -------------- | ----------------------------------- |
| 掃描裝置       | 清單出現你的 ACR1555U               |
| 點選連線       | 顯示 connected / ATR 或 card status |
| 執行認證       | 成功，無錯誤                        |
| 把卡放上感應區 | 讀到 UID                            |

### 2.3 ⭐ 順便確認這幾件事（全部是純讀取）

demo app 通常有 APDU / Escape 輸入欄。以下指令都是**讀取**，不會消耗任何認證額度：

| 指令             | 用途            | 預期回應          |
| ---------------- | --------------- | ----------------- |
| `E0 00 00 18 00` | 取固件版本      | `E1 …` + 版本字串 |
| `E0 00 00 47 00` | 取序列號        | `E1 …` + SN       |
| `E0 00 00 44 00` | 取 BLE 廣播名稱 | 確認你連到哪一台  |
| `E0 00 00 52 00` | 取電量          | 現場前確認電量    |
| `E0 00 00 43 00` | 取 MAC          | 記錄用            |

**把這幾項記下來**，特別是固件版本——它決定你的機器符合哪一版手冊。

> ⚠️ **V2.02 沒有 `Read Authentication Error Counter`。**
> 前一版 Runbook 叫你送 `E0 00 00 72 00` 讀錯誤額度——**那句已作廢**。
> 現在的立場是：**沒有辦法事先知道還剩幾次，所以不要試錯。**

### 2.4 這一步的四種結果

| 結果                     | 意思                         | 下一步                                     |
| ------------------------ | ---------------------------- | ------------------------------------------ |
| 全部成功                 | ✅ 硬體鏈沒問題              | 進 §3（網頁）或 §4（App）                  |
| 掃不到裝置               | BLE 沒進可搜尋狀態，或被佔住 | 回 §1.1                                    |

## 3. 網頁測試（你要的「在前端 website 上測試」）

### 3.1 先說清楚現在能做什麼、不能做什麼

| 能力                                                  | 現在                     | 原因           |
| ----------------------------------------------------- | ------------------------ | -------------- |
| 連線 + 列出 GATT                                      | ✅ **現在就能**          | 純讀取，零風險 |
| 讀 UID / 讀寫卡片                                     | ⬜ 需先確認 service UUID | 見下           |
| 在現有 `/check-in/[eventId]/nfc` 加「讀卡機讀取」按鈕 | ⬜ 要等上一步            | 先把輸入源搞定 |

### 3.2 用探測器（已放在 repo）

工具：`tools/nfc-web-probe/probe.html`（說明見同資料夾 `README.md`）

**它在做什麼**：連上讀卡機 → 列出所有 service 與 characteristic → 印出來。
**它不做什麼**：不認證、不寫卡、不送任何自組訊框 ⇒ **不可能消耗錯誤額度**。

#### 平板怎麼開（Web Bluetooth 必須 HTTPS）

| 做法                                            | 時間   | 備註                  |
| ----------------------------------------------- | ------ | --------------------- |
| 拖到 **Cloudflare Pages / Netlify Drop**        | 2 分鐘 | 最快，取得 HTTPS 網址 |
| `python3 -m http.server` + `cloudflared tunnel` | 5 分鐘 | 不部署                |
| 放進前端 `public/`                              | 2 分鐘 | ⚠️ 會上生產，測完刪   |

#### 操作與判讀

1. 讀卡機進 BLE 模式（藍燈閃）
2. 開頁面 → **「1. 搜尋並連線讀卡機」** → 選裝置
3. **「2. 列出所有 service 與 characteristic」**
4. 把輸出**複製保存**

| 看到什麼                                      | 意思                                                               |
| --------------------------------------------- | ------------------------------------------------------------------ |
| `▸ SERVICE 00003970-…` + 三條 characteristic  | ✅ **service UUID 確認**，可以進 §3.3                              |
| 一個 service 都沒找到                         | service UUID 不是 `3970`。把 `CANDIDATE_SERVICES` 加上其他候選再試 |
| `3971` 顯示 `[write]`、`3972` 顯示 `[notify]` | ✅ 與手冊一致，pipe 方向確認                                       |
| 斷線後按「3. 重新連線」失敗                   | ⚠️ U3 的答案就是「不能」，現場要改用別的裝置                       |

### 3.3 為什麼現在不要直接寫一個能寫卡的網頁

有**兩個**阻礙，而且第二個是這輪新發現的。

#### 阻礙一：傳輸框架的 checksum 欄位名不一致

手冊 §5.2.3 的 checksum 說明寫「槽位、長度、**幀類型**、主機&讀寫器序列號和數據域」，
但表格裏那個位元組叫 **保留（Reserved）**——同一個位置兩個名字，兩版手冊（V1.06 / V2.02）
都這樣寫。**算錯就整框被丟棄，而且沒有任何錯誤訊息。**

而官方 SDK 的實作包在 AAR 裏，看不到原始碼。

#### 阻礙二（更硬）：V2.02 把認證協定移出公開手冊

V1.06 有完整的四步認證（含 `E0 00 00 73 00`）。
**V2.02 只剩一張流程圖，並指向另一份文件：**

> 「如需獲取更詳細的信息，請參考**《開發者指南：雙向認證與安全數據交換》**。
> 您也可以聯繫 ACS 銷售代表。」

⇒ 要自己實作網頁版認證，**需要向 ACS 索取那份開發者指南**。
照 V1.06 的舊值去猜，而錯誤代價是**讀卡機報廢**（見 §0 與 `21-*.md` §4）。

#### 所以正確順序是

```
1. 用官方 SDK 跑通（§2）           ← 今天就能做
2. 用探測器確認 UUID / pipe（§3.2） ← 今天就能做
3. 向 ACS 索取《開發者指南》        ← 發一封信
4. 有指南之後，才實作網頁認證       ← 之後的事
```

**這不是拖延，是唯一安全的路徑。** 沒有第 3 步，第 4 步就是在賭一台讀卡機。

### 3.4 現有網頁已經有的東西（不用重做）

`LinkCard_Frontend/app/check-in/[eventId]/nfc/page.tsx` 已經有：

- `tagUid` 文字輸入框（`:121-124`）
- `POST /nfc/bind` 接線
- 錯誤處理（`BADGE_ALREADY_BOUND` 等）

⇒ 網頁端**只缺「把 tagUid 從讀卡機填進去」這一段**。
一旦 §3.2 確認 service UUID，這就是一個小改動，不是新功能。

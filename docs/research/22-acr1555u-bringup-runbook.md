## 1. 硬體準備（10 分鐘）

### 1.1 讀卡機進入 BLE 可被搜尋狀態

> 以下照 `USR-ACR1555U-A1-1.07-CN.pdf` §3（官方使用者手冊原文）。

```
1. 長按「電源開關」3 秒
   → 綠燈「常亮」  = 已開機
   → 藍燈「開始閃爍」= 可被偵測 ✅

2. 若「綠燈亮但藍燈不閃」
   → 長按「模式開關」3 秒，進入藍牙模式
```

| LED 狀態                | 意思                               |
| ----------------------- | ---------------------------------- |
| 綠燈常亮 + **藍燈閃爍** | ✅ 可被搜尋，去做 §2               |
| 綠燈常亮 + **藍燈常亮** | 已被某台裝置連上（可能是你的筆電） |
| 綠燈滅                  | 沒開機或沒電                       |

> ⚠️ **「長按 MODE 4 秒可清除綁定」這個說法我查不到官方依據。**
> 它來自先前的研究文件，但 `USR V1.07` 沒有這樣寫。
> 官方的清除方式是**用 Windows 的 Configuration Tool**（手冊 §4.2），
> 或用指令 `E0 00 00 5B 00`（但手冊註明**僅限 USB 模式**）。

### 1.1b ⚠️ 如果你之前玩過 HID 模式

手冊 §4.2 附近有一句很重要的話：

> 「要切換回 NFC 讀寫器模式，請按照說明**清除綁定（配對）記錄**。」

⇒ **HID 鍵盤模式不會自己退出。** 想切回 APDU 模式，得用 Windows 工具清除配對。
**所以：先不要在平板系統設定裏把它配對成鍵盤。**

### 1.2 平板端

| 設定                   | 為什麼                                              |
| ---------------------- | --------------------------------------------------- |
| 藍牙 **開**            | 基本                                                |
| **定位（Location）開** | Android 把 BLE 掃描歸類為可能洩漏位置，關掉會掃不到 |

### 1.3 讀卡機接法

讀卡機是 **USB Type-C**，且有**內建充電電池** ⇒ 用 BLE 時不用插線，
不會吸平板電。第一次用之前建議先插 USB 充飽（`E0 00 00 52 00` 可讀電量）。

### 1.4 卡片相容性：NTAG215 可以用嗎？

**可以。** 但我要把舉證方式講清楚，因為原廠文件**從頭到尾沒有出現「NTAG」這個字**。

#### 證據鏈（三條獨立線索都指向同一個結論）

| #   | 來源                       | 原文                                                                                                                                  | 推論                                                                       |
| --- | -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| 1   | `REF V2.02` §3 產品特性    | 「支持 ISO 14443 第 4 部分 A 類和 B 類卡、MIFARE® 系列卡、FeliCa 卡和**全部五種 NFC（ISO/IEC 18092）標籤**」                          | NTAG213/215/216 是 **NFC Forum Type 2** ⇒ 屬「五種 NFC 標籤」之一          |
| 2   | `TSP 1.09` 支援卡片類型    | 「ISO 14443 A 類 & B 類 **1-4 部分**」                                                                                                | NTAG215 是 ISO/IEC 14443-3 Type A ⇒ 在第 1-4 部分範圍內                    |
| 3   | `REF V2.02` §5.5.3 + 表 14 | 有 **MIFARE Ultralight 記憶體結構表** 與 `FF B0` / `FF D6` 讀寫範例；並註明「MIFARE Ultralight 不需要進行驗證，其記憶體可以自由訪問」 | NTAG 與 Ultralight **共用同一套記憶體指令**（`30` 讀 / `A2` 寫）與頁面模型 |

#### 對應到實際 APDU（V2.02 §5.5.3.4 / §5.5.3.5）

| 操作 | APDU                              | 手冊範例                                         |
| ---- | --------------------------------- | ------------------------------------------------ |
| 讀   | `FF B0 00 <起始頁> <長度>`        | `FF B0 00 04 10`（讀 16 bytes）                  |
| 寫   | `FF D6 00 <起始頁> <長度> <資料>` | Ultralight 4 bytes：`FF D6 00 04 04 00 01 02 03` |

⚠️ Ultralight/NTAG 的**讀取上限是 16 bytes**（4 的倍數）。
NTAG215 有 504 bytes 使用者記憶體 ⇒ 要整片讀完得分多次讀，但**我們的用途不需要**。

#### NTAG215 容量夠不夠？

| 項目                 | 數值                                         |
| -------------------- | -------------------------------------------- |
| NTAG215 使用者記憶體 | 504 bytes（Page 4–129）                      |
| 我們的 NDEF 內容     | URI 一條 + TLV 包頭，約 **40–70 bytes**      |
| 結論                 | **綽綽有餘**（連 NTAG213 的 144 bytes 都夠） |

NTAG213/215/216 的差別只在容量，指令與頁面模型完全相同 ⇒ **三者都適用**。

#### ⚠️ 這條結論的等級

| 等級                    | 說明                                                                             |
| ----------------------- | -------------------------------------------------------------------------------- |
| ✅ **高信度**           | 三條獨立證據都支持，且 APDU 層有原廠範例                                         |
| ⚠️ **但不是「已驗證」** | **手冊沒有明文列出 NTAG**。這是由「五種 NFC 標籤 + Ultralight 記憶體模型」推得的 |

⇒ **最終確認方式是實測**（§2 第 4 步）：拿一張 NTAG215，用官方 demo 讀看看有沒有回應。
這也正是 `21-*.md` 的 **U7**（`FF B0`/`FF D6` 在 NTAG 上是否與 Ultralight 一致）要回答的問題。

> 若實測失敗，不一定是讀卡機不支援——先確認卡片是 **NTAG215 而非 NTAG215 的仿製品**，
> 以及是否為 **ISO 14443-3 Type A**（不是 Type B、也不是 15693）。

### 3.3 這兩個阻礙現在怎麼處理的

> **2026-10-22 更新**：原本這節的標題是「為什麼現在不要直接寫一個能寫卡的網頁」。
> 那個結論已經被推翻了——前端 `/nfc` 就是一個能寫卡的網頁。以下是兩個原本的阻礙
> 與後來的處理方式，保留原文是因為**判斷錯在哪裡**比結論本身更有價值。

一開始有**兩個**阻礙，而且第二個是那輪新發現的。兩個都已經解决，但方式不同：一個
靠設計繞過，一個靠查原文推翻。

#### 阻礙一：傳輸框架的 checksum 欄位名不一致 → **用可切換參數繞過**

手冊 §5.2.3 的 checksum 說明寫「槽位、長度、**幀類型**、主機&讀寫器序列號和數據域」，
但表格裏那個位元組叫 **保留（Reserved）**——同一個位置兩個名字，兩版手冊（V1.06 / V2.02）
都這樣寫。**算錯就整框被丟棄，而且沒有任何錯誤訊息。**

而官方 SDK 的實作包在 AAR 裏，看不到原始碼。

**處理方式**：不去猜名字，只看**位元組位置**。`lib/nfc/protocol.ts` 把 offset 4 叫
`reserved`（依表格），並讓 `parseFrame` 回傳**實際位元組**——這樣實機一回應就能看出
那個位元組實際上是什麼值。另外外層 `Len` 的位元組序手冊完全沒寫，所以
`buildFrame` 把它做成 `lengthEndian` 參數。

⇒ **2026-10-23 實機結案：`Len` 是 big-endian，預設已改為 `'be'`。**
決定性的是這條 19 bytes 回應（送 `FF 00 00 00 01 60` 之後收到）：

```
55 00 00 0A 00 00 00 | 53 00 00 00 00 00 00 02 07 00 | 5C | AA
       ↑↑↑↑
      00 0A = 10（BE）＝後方 datablock 實長
```

讀成 little-endian 會得到 2560，解析器於是永遠停在「還沒收完」→ 3 秒逾時，
錯誤訊息是「等不到讀卡機回應」。**真相是讀卡機每一則都有回，是我們把它們丟掉了。**
同樣的預設也讓送出的 request 被讀卡機拒絕（`10 00` 被讀成 4096），所以兩邊一起錯，
症狀才長得那麼像硬體故障。

注意 checksum 在這裡的角色：XOR 與位元組序無關，所以 `0x5C` 對得上只證明欄位邊界
正確，**不能**單獨證明位元組序。要有「長度讀成 10 才自洽」這第二個事實才算證明。

⇒ 這兩條實機訊框已固化成回歸測試（`lib/nfc/__tests__/protocol.test.ts`），
避免有人「順手」把它改回 LE 而測試全綠。

#### ~~阻礙二（更硬）：V2.02 把認證協定移出公開手冊~~ → **已釐清，這不是阻礙**

我原本把「認證」當成讀寫卡片的前置條件。**看原文後發現不是。**

`REF V2.02` §5.2.5：

> **如果啟用了強制加密**，向 ACR1555U 載入敏感資料之前，資料處理伺服器必須通過
> ACR1555U 的認證，**才有權修改讀寫器內部的安全資料**。

而且表 8 對每一條命令（含 `6Fh` Exchange APDU）都標「**明文, 已認證**」——兩種模式都接受。

⇒ **讀卡／寫卡走明文即可，不需要認證，也就不需要那份《開發者指南》。**
那份指南只在你要**改讀卡機設定／換主金鑰**時才需要。

**實測已佐證**：2026-10-22 的測試中，`6Fh` 在沒有做任何認證的情況下成功送達卡片
並取得回應（見 §5）。

| 你要做的事             | 需要認證 | 需要《開發者指南》 |
| ---------------------- | -------- | ------------------ |
| 讀 UID／讀 NDEF        | ❌       | ❌                 |
| 寫 NDEF                | ❌       | ❌                 |
| 改讀卡機設定、換主金鑰 | ✅       | ✅                 |

> ⚠️ 唯一未確認的前提：讀卡機是否被設成**強制加密**模式。
> 若是，明文命令可能被拒。這用下一節的實測就能知道。

#### 所以正確順序是

```
1. 用官方 SDK 跑通（§2）           ← 今天就能做
2. 用探測器確認 UUID / pipe（§3.2） ← 今天就能做
3. 向 ACS 索取《開發者指南》        ← 發一封信
4. 有指南之後，才實作網頁認證       ← 之後的事
```

**這不是拖延，是唯一安全的路徑。** 沒有第 3 步，第 4 步就是在賭一台讀卡機。

### 5.2 判讀：連線成功，腳本不對

| 現象                                      | 判讀                                                                                               |
| ----------------------------------------- | -------------------------------------------------------------------------------------------------- |
| `Terminal: ACR1555U-A1-000688 PICC`       | ✅ BLE 已連上，PICC 卡槽已選取                                                                     |
| `Connecting to the card` → **ATR 有回應** | ✅ **卡片已上電並被選取**——這是最硬的證據                                                          |
| `Active Protocol: T=1`                    | ✅ 與 ATR 內的 `TD2 = 01h`（T=1）一致                                                              |
| `Response: 6A 81`                         | ⚠️ **不是連線錯誤**。`6A 81` = 「功能不支援」，因為 `acos3.txt` 是 **ACOS3 卡片**的腳本，不是 NTAG |
| `Error: Unexpected response`              | 腳本期待 `90 00`，但 NTAG 不可能回應 ACOS3 指令                                                    |

⇒ **這是一次成功的連線測試**，只是拿錯腳本。硬體鏈（平板 → BLE → 讀卡機 → 卡片）**已全通**。

### 5.3 ⭐ ATR 直接證明 NTAG216 被辨識為 MIFARE Ultralight

依 `REF V2.02` §5.5.1.1 的 ATR 格式逐位組解：

| 位元組 | 值               | 欄位         | 說明                                        |
| ------ | ---------------- | ------------ | ------------------------------------------- |
| 0      | `3B`             | TS           | 初始字元                                    |
| 1      | `8F`             | T0           | 15 個歷史字元                               |
| 2      | `80`             | TD1          | T=0                                         |
| 3      | `01`             | TD2          | **T=1** ← 對應畫面的 `Active Protocol: T=1` |
| 4      | `80`             | T1           | 類別指示                                    |
| 5      | `4F`             | —            | 應用識別碼                                  |
| 6      | `0C`             | —            | 長度 12                                     |
| 7–11   | `A0 00 00 03 06` | RID          | PC/SC 工作組                                |
| 12     | `03`             | SS           | **ISO 14443A，第 3 部分**                   |
| 13–14  | **`00 03`**      | **卡片名稱** | **`00 03h = MIFARE Ultralight®`**           |
| 15–18  | `00 00 00 00`    | RFU          | —                                           |
| 19     | `68`             | TCK          | T0–Tk 的 XOR（已驗算：`0x68` ✓）            |

⇒ **讀卡機自己把 NTAG216 歸類為「MIFARE Ultralight」。**
這正好就是 §5.5.3 那組 `FF B0` / `FF D6` APDU 所操作的卡片類型。

**所以 `21-*.md` 的 U7 由硬體本身回答了：**

> NTAG216 走 Ultralight 分支，`FF B0`（讀）/ `FF D6`（寫）就是正確的 APDU。

### 5.5 你的下一步：三個 APDU，就能確定能不能寫卡

在官方 `BLETest` app 裏，把 **Source 由 `Script` 改成 `Input`**，然後依序送這三條。
**都是明文、不需要認證——所以不會碰到鎖機風險。**

#### ① 取 UID

```
FF CA 00 00 00
```

| 回應      | 意思                                                                              |
| --------- | --------------------------------------------------------------------------------- |
| `… 90 00` | ✅ 卡片有回應，UID 就是 `90 00` 前面的 bytes                                      |
| `6A 81`   | ⚠️ 不支援這個指令——但這對 NTAG 而言是**正常的**（NTAG 用 `30 xx` 讀 UID），改測 ② |
| 無回應    | 卡沒貼好，或讀卡機需要重新選卡                                                    |

#### ② 讀 NDEF 區（關鍵測試）

```
FF B0 00 04 10
```

從 **Page 4** 讀 16 bytes。這是 Ultralight/NTAG 的使用者資料起點。

| 回應               | 意思                                                          |
| ------------------ | ------------------------------------------------------------- |
| 16 bytes + `90 00` | ✅✅ **APDU 層通了**，`FF B0` 可用                            |
| `6A 81` / 其他錯誤 | `FF B0` 這條路不通，改試 pass-through：`FF 00 00 00 02 30 04` |

> 全新未寫過的卡，Page 4 通常是 `03 00 FE 00 …`（空 NDEF TLV）或全 `FF`。
> 已經寫過 NDEF 的卡，會看到 `03 <長度> D1 01 …`。

#### ③ 寫入測試（**只在②成功後才做**）

選一張**可以報廢的**卡片，寫 4 bytes 到 Page 4：

```
FF D6 00 04 04 00 00 00 00
```

| 回應              | 意思                                  |
| ----------------- | ------------------------------------- |
| `90 00`           | ✅✅✅ **寫入通了，整套方案成立**     |
| `69 82` / `69 81` | 卡片寫入保護中（lock bits），換一張卡 |
| `63 00`           | 寫入失敗                              |

寫完再送一次 ② 讀回來，確認 bytes 真的變了——**只看 `90 00` 不算成功**。

#### 三條都通之後

| 下一步                  | 說明                                                  |
| ----------------------- | ----------------------------------------------------- |
| ✅ 可以開始做網頁版     | 用 §3.2 的探測器確認 GATT，再照 `21-*.md` §5 實作框架 |
| ✅ 可以把 `U7` 正式關閉 | 目前是「由 ATR 高度推定」，實測後就是「已驗證」       |

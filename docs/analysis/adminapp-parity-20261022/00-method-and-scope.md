本目錄是一次 **App ↔ Web ↔ Backend 三方功能／契約對等審計** 的完整證據鏈。
目的：回答「Expo 門側 App 的功能是否已與 Web 前端一致、接 API 的方式是否一模一樣」。

## 三種「一致」要分開講

這是本輪最重要的方法論決定。混在一起講會得到錯誤結論。

1. **端點一致（endpoint parity）** — App 呼叫的路徑與方法，後端真的存在嗎？
   - 可機械判定，有唯一答案。**本輪發現 1 條 404。**
2. **語意一致（semantic parity）** — 同一條端點，兩邊送的 payload、query、讀回的欄位、處理的錯誤碼一樣嗎？
   - 可逐欄比對。**本輪發現 6 處漂移。**
3. **功能一致（capability parity）** — 兩邊各自能做哪些事？
   - **這一層不可能「一樣」**，因為兩個客戶端的存在理由不同。要問的是「差異是否被明示」。

> 因此「功能是否基本上完全一致」的正確答案是：**端點與語意層應該 100% 一致（可驗證）；功能層不該一致，但差異必須被記錄成「刻意差異」。**

## 取證方式（全部可重跑）

```bash
# Backend route table（121 條）
python3 -B /tmp/parity/extract_be.py

# Frontend endpoint literals（78 個）
python3 -B /tmp/parity/extract_fe.py

# App ↔ BE 覆蓋率
python3 -B /tmp/parity/coverage.py
```

三支腳本都是**純讀取**（`python3 -B` 關閉 bytecode 寫入，避免污染受測 repo）。
這是 2026-10-19 的教訓：驗證別人交付的目錄時先假設它會寫檔。

## 判定規則（先講清楚，避免事後各自解讀）

一個差異要歸到哪一類，用這三題依序問：

| 問題                                | 是                   | 否                    |
| ----------------------------------- | -------------------- | --------------------- |
| Q1 後端有這條路由嗎？               | 往下問 Q2            | **契約漂移（P0）**    |
| Q2 兩邊送／收的形狀一樣嗎？         | 往下問 Q3            | **契約漂移（P1）**    |
| Q3 這個能力屬於「門側現場」職責嗎？ | **刻意差異（記錄）** | **未實作（backlog）** |

「門側現場」的操作型定義：**在活動現場、以手機、由工作人員執行、需要在 30 秒內完成**的事。
報到、寫卡、換名片、現場報名、查名單屬之；票種設定、議程編排、參展商頁面編輯不屬之。

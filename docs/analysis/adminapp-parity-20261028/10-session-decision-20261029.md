## 10.2 用現場情境說

你的活動有工作坊，每場有座位上限。參加者**事前**上網報名某一場，名額當場扣——額滿
時後端直接回「已滿員」，不是到現場才發現。

活動當天，工作坊門口需要有人確認一件事：**「這個人真的來了嗎？」**

系統現在只答得出一半：知道**誰報名了**，不知道**誰真的來了**。這是兩個不同的東西
——報名是資料表裡的一列，出席是那一列上的 `attended_at` 有沒有被寫入。

## 10.4 你要回答的是兩層，不是一層

**第一層（關鍵——只有這一層必答）：你們的活動有沒有「場次」？**

- **沒有** → G-9 從登記表移到 `BY_DESIGN`（＝確認永遠不做，下一輪不再問你）。這是
  最乾淨的結局，也省下所有後續討論。
- **有** → 才需要進第二層。

**第二層（只有答「有」才需回答）：你要「事後知道誰來了」，還是「門口擋人」？**

|             | A：出席紀錄                       | B：門口擋人                             |
| ----------- | --------------------------------- | --------------------------------------- |
| 解決什麼    | 賽後知道誰真的來了                | 客滿時把沒報名的人擋在門外              |

| 技術現況    | **後端已就緒**，只缺 App 一個畫面 | 後端要加「設計過的拒絕」＋「強制放行」  |
| 要新 API 嗎 | **不用**                          | 要                                      |

關於 B 的誠實補充：現在掃一個沒報名的人，後端回 404
（`LinkCard_ExpressJS_Backend@src/events/constants/sessionErrors.ts:56`）。但那不是
「擋人」，那是「查不到」。B 要的是門口那個人看得懂的拒絕，加上一個能當場放行的覆寫
——後者目前不存在。

## 10.5 選 A 的真正理由（如果你要說服別人）

1. **它是這幾個決策裡唯一門口工讀生真的用得到的能力**——而且他今天已經拿著 App 在
   掃活動報到了，只差場次那一層。
2. **後端完全就緒，不用等任何人。** 不用排後端工期、不用改 schema、不用改權限。
3. **出席時間戳事後無法重建**——這是唯一「錯過就沒有」的資料。要申請補助、發學分、
   跟贊助商結報「實際接觸人數」，這張表是必要證據；活動結束後補不出來。

## 10.6 選「都不需要」也是完整答案——但要連端點一起處理

不要留著孤兒端點。它會腐化：schema 改了沒人知道、權限設定了沒人記得、下一個人以為
有人在用。

⚠️ **刪除不是刪一行路由。** 實際掃過的連帶範圍是 **9 個檔案**：路由、controller、
service、錯誤碼表，3 支單元測試（其中一支專門測併發），以及 2 支 QA script。這比
「順手刪掉」貴，但比留著腐化便宜——而且它是**一次性的**。

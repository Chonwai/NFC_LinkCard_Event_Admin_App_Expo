## 7.1 你問的問題，我改成三個問題

原文是「App 是不是基本上和 Web Event Admin 一模一樣，沒有一樣就要對齊」。

這句話有兩個陷阱。第一個：「一模一樣」對兩個不同用途的客戶端不是目標——Web 是
主辦方的設定與財務後台，App 是活動當天的門口櫃檯，把 13 個 Web 模組搬進手機不會
讓現場變快。第二個：如果只比「有沒有這個畫面」，會漏掉真正會傷人的東西——呼叫
一條不存在的路由、顯示一個後端根本沒送的欄位。

所以拆成三層，每層有不同的正確答案：

| 層   | 問句                   | 該不該一樣 | 判準                 |
| ---- | ---------------------- | ---------- | -------------------- |
| 端點 | 是不是在打同一條路     | 該，100%   | 契約存在即可機械判定 |
| 語意 | 送出與收回的形狀一樣嗎 | 該         | 對照後端投影         |
| 能力 | 各自能完成哪些工作     | 不該       | 要一個可反駁的理由   |

## 7.2 結論：沒對齊，而且這一週差距擴大

一句話版本：**Web 這個星期把「門口櫃檯」補完了，App 沒有跟上。**

具體是什麼被補完：Web 的報到畫面現在掃碼成功之後**不必離開這一頁**就能寫卡、綁卡，
並且在**寫入的同時**設定卡片密碼；App 仍然是掃碼後跳另一個頁面寫卡，而且完全沒有
上鎖能力。上一輪（10-22）把這件事記成「App 是超集、Web 結構性做不到」，那個判定
在 10-27 之後失效了。

「不用離開這一頁」的實際意思是**同一個頁面、同一條藍牙連線**，不是「三個元素從頭
同框」：讀卡機狀態條在所有狀態下常駐（`app/check-in/[eventId]/page.tsx:707`），
寫卡面板要**掃到人之後**才出現在成功卡裡（`app/check-in/[eventId]/page.tsx:866`）。
上鎖也不是對既有的卡另外做一次 `PWD_AUTH`，而是發卡序列的一部分——寫入 → 逐 byte
讀回 →（上鎖）（`hooks/useNfcReader.ts:690-722`、`lib/nfc/issue.ts:179`）。

## 7.3 我怎麼得到這個答案（四道關卡）

我不想讓結論只靠「我讀完了」。

1. **先找前例，不重做。** 10-22 有一輪同題審計，28 個 commit。我先確認它在哪、
   量了什麼，然後只做兩件事：重測它的每個事實、量它量不到的一週。
2. **機械量測取代記憶。** 端點用既有的契約閘門對今日原始碼跑一次；後端路由用
   快照重新產生再逐條比對，得到「121 → 122，唯一新增 `manage-stats`」。這兩個
   數字不是抄來的。
3. **獨立複核。** 另一個 agent、另一個 process，只給工單不給結論，重跑 10 條斷言。
   結果 10/10 PASS，但它抓到兩個**表述**問題（不是事實問題），見 §7.7。
4. **把判定變成可重跑的檢查。** 這是「最少技術債」的落點：加一份能力登記表與閘門，
   Web 出現沒登記的頁面就讓建置變紅。**表格會自己過期**；閘門只抓得到「Web 新增頁面
   沒登記」，同一個頁面長出新能力它不會叫——那一類只能靠人重測。

## 7.6 為什麼我不建議「全部對齊」

> ⚠️ **本節建議已於 2026-10-29 被使用者推翻。** 下面兩段保留原文，作為「當時看到
> 的代價」的記錄；決定改為全面功能對齊，理由與驗收定義見
> `11-full-parity-decision-20261029.md`。本節列出的代價沒有消失，它們變成動工前的
> 前置條件（`03-capability-matrix.md` §3.7.8）。

九個 `BY_DESIGN` 裡有八個是同一類理由：那些工作需要在活動**之前**、用大螢幕、
看得到完整上下文的情況下做。手機不是不合適而已，是會做錯。

**第九個（Sessions）不是這一類，不要混進去。** 它不是「手機不合適」，是
**活動沒有「場次」這個單位**，所以那個功能沒有對象（2026-10-29 已決，`by-design`）。
兩類理由的差別見 `03-capability-matrix.md` §3.6 末的小表。

反過來說，這九條都可以被推翻。推翻的方式不是「Web 有所以 App 也要有」，而是給我
一個具體情境，例如「活動當天贊助商臨時要換 logo，人在現場只有手機」。有了那個
情境，判定就該改。（Sessions 的推翻方式是另一種：證明活動真的有多場次。）

三個 `APP_GAP` 裡，只有一個（Badges）是比較單純的「能力缺」；另外兩個其實是
**政策問題**：名單可以讓門口人員封存嗎？報到桌要不要在 App 上寫卡與上鎖？
這兩個不該由實作進度決定。

## 7.7 我認為自己可能錯的地方

1. **行為層完全沒驗。** 這一輪是靜態審計：沒有真機、沒有讀卡機、沒有 staging
   帳號。「Web 能在報到畫面寫卡」是讀程式碼得出的，不是操作得出的。
2. **獨立複核挑出我一句過度陳述。** 我寫「產品碼與 main 逐位元相同」，依據是一條
   我自己挑的路徑清單；那條分支對 main 的差異在複核當時（`58affea`）是 43 檔、
   +7,994 行，`44f6bd9` 上是 **62 檔、+11,656 行**（多出來的是本輪自己加的登記表
   閘門與測試，以及後續文件），兩種都包含 lint 設定。已改成逐步列出差異。這件事的
   意義是：**PASS 不等於我那句話成立**。
3. **122 條路由是產生器的輸出。** 產生器曾漏收 8 條巢狀路由（上一輪修過）。本輪
   的結論對「漏收」不敏感（我比的是差異），但絕對值仍然依賴它。
4. **產業對照沿用上一輪的六家研究**，沒有重跑。

  `M`；**若財務要求雙人核可**（後端目前只記一位操作者），則升為 `L`。選它等於

**不決定 ⇒ 默認 A**：名單只能看，退款與封存一律回 Web。

**3. 報到桌要不要在 App 上寫卡與上鎖？（G-8，兩選項見 §G-8）** 這一題的問法
2026-10-29 校準過：**App 已經會寫卡**（報到結果卡的「寫入 NFC 卡」CTA 把報名碼帶進
`nfc-bind`，`check-in.tsx:673-685`，有測試釘住），所以它問的其實是**兩頁還是一頁、

- **A｜維持現況（兩頁、不上鎖）**：每張卡多一次點擊與一次換頁，而且**漏按沒有提示**；
  卡片沒有密碼保護。零新風險、工期近 `S`。選它等於承認「報到後的寫卡可以是一個
  需要人記得的步驟」。
- **B｜收進同一頁，並加上鎖**：先過三個前置 ① APDU 中斷回復要真機驗 ② iOS 不可能，

  能發卡」，並接受兩個平台的完成度不同。

**不決定 ⇒ 默認不上鎖（現況）**：Android 能寫不能鎖，iOS 只有 QR。

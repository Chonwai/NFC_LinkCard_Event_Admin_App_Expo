## 7.1 你問的問題，我改成三個問題

原文是「App 是不是基本上和 Web Event Admin 一模一樣，沒有一樣就要對齊」。

這句話有兩個陷阱。第一個：「一模一樣」對兩個不同用途的客戶端不是目標——Web 是
主辦方的設定與財務後台，App 是活動當天的門口櫃檯，把 13 個 Web 模組搬進手機不會
讓現場變快。第二個：如果只比「有沒有這個畫面」，會漏掉真正會傷人的東西——呼叫
一條不存在的路由、顯示一個後端根本沒送的欄位。

所以拆成三層，每層有不同的正確答案：

| 層   | 問句                   | 該不該一樣 | 判準                 |
| ---- | ---------------------- | ---------- | -------------------- |
| 端點 | 是不是在打同一條路     | 該，100%   | 契約存在即可機械判定 |
| 語意 | 送出與收回的形狀一樣嗎 | 該         | 對照後端投影         |
| 能力 | 各自能完成哪些工作     | 不該       | 要一個可反駁的理由   |

## 7.2 結論：沒對齊，而且這一週差距擴大

一句話版本：**Web 這個星期把「門口櫃檯」補完了，App 沒有跟上。**

具體是什麼被補完：Web 的報到畫面現在掃碼成功之後**不必離開這一頁**就能寫卡、綁卡，
並且在**寫入的同時**設定卡片密碼；App 仍然是掃碼後跳另一個頁面寫卡，而且完全沒有
上鎖能力。上一輪（10-22）把這件事記成「App 是超集、Web 結構性做不到」，那個判定
在 10-27 之後失效了。

「不用離開這一頁」的實際意思是**同一個頁面、同一條藍牙連線**，不是「三個元素從頭
同框」：讀卡機狀態條在所有狀態下都常駐（`app/check-in/[eventId]/page.tsx:717`），
寫卡面板要**掃到人之後**才出現在成功卡裡（`app/check-in/[eventId]/page.tsx:876`）。
上鎖也不是對既有的卡另外做一次 `PWD_AUTH`，而是發卡序列的一部分——寫入 → 逐 byte
讀回 →（上鎖）（`hooks/useNfcReader.ts:690-722`、`lib/nfc/issue.ts:179`）。

## 7.3 我怎麼得到這個答案（四道關卡）

我不想讓結論只靠「我讀完了」。

1. **先找前例，不重做。** 10-22 有一輪同題審計，28 個 commit。我先確認它在哪、
   量了什麼，然後只做兩件事：重測它的每個事實、量它量不到的一週。
2. **機械量測取代記憶。** 端點用既有的契約閘門對今日原始碼跑一次；後端路由用
   快照重新產生再逐條比對，得到「121 → 122，唯一新增 `manage-stats`」。這兩個
   數字不是抄來的。
3. **獨立複核。** 另一個 agent、另一個 process，只給工單不給結論，重跑 10 條斷言。
   結果 10/10 PASS，但它抓到兩個**表述**問題（不是事實問題），見 §7.7。
4. **把判定變成可重跑的檢查。** 這是「最少技術債」的落點：加一份能力登記表與閘門，
   Web 出現沒登記的頁面就讓建置變紅。表格不會自己過期，但可以被強迫更新。

這一輪之所以要花時間重判，是因為上一輪的結論沒有人負責讓它保持正確。

這張表讀的是「**現在的狀態**」，不是登記冊的 `status` 欄位——標成
`fixed-on-branch` 的六項在 HEAD 上仍然存在，判準與逐項證據見
`04-gap-register.md §4.1` 的說明框。

「報到桌寫卡」這一格最容易讀成錯的畫面：Web 的優勢不是「三個步驟擠在同一畫面」，
而是**同一個頁面、同一條連線**——掃到人之後寫卡面板才出現，上鎖是寫入的一部分。
App 要做同一件事得換頁、斷一次連線，而且不能上鎖。

另外三個 App 獨有：現場報名、卡片交換、手機感應讀 UID。

有一個判定要**撤回**：上一輪把「Token 帳本」列為 App 的差異化。讀了原始碼之後
發現那一頁是 placeholder，而且它的次要按鈕會開一條 Web 沒有的路由。它不能被算成
能力。

## 7.6 為什麼我不建議「全部對齊」

八個 `BY_DESIGN` 不是偷懶，是同一個理由重複八次：那些工作需要在活動**之前**、
用大螢幕、看得到完整上下文的情況下做。手機不是不合適而已，是會做錯。

反過來說，這八條都可以被推翻。推翻的方式不是「Web 有所以 App 也要有」，而是給我
一個具體情境，例如「活動當天贊助商臨時要換 logo，人在現場只有手機」。有了那個
情境，判定就該改。

四個 `APP_GAP` 裡，只有兩個是「能力缺」；另外兩個其實是**政策問題**：名單可以讓
門口人員封存嗎？報到桌要不要在 App 上寫卡與上鎖？這兩個不該由實作進度決定。

## 7.7 我認為自己可能錯的地方

1. **行為層完全沒驗。** 這一輪是靜態審計：沒有真機、沒有讀卡機、沒有 staging
   帳號。「Web 能在報到畫面寫卡」是讀程式碼得出的，不是操作得出的。
2. **獨立複核挑出我一句過度陳述。** 我寫「產品碼與 main 逐位元相同」，依據是一條
   我自己挑的路徑清單；實際上那條分支對 main 有 43 檔、+7,994 行差異，其中包含
   lint 設定。已改成逐步列出差異。這件事的意義是：**PASS 不等於我那句話成立。**
3. **122 條路由是產生器的輸出。** 產生器曾漏收 8 條巢狀路由（上一輪修過）。本輪
   的結論對「漏收」不敏感（我比的是差異），但絕對值仍然依賴它。
4. **產業對照沿用上一輪的六家研究**，沒有重跑。

## 7.8 方案：四個階段，順序有意義

| 階段 | 做什麼                           | 為什麼在這個位置                   |
| ---- | -------------------------------- | ---------------------------------- |
| 一   | 登記表＋閘門上 CI                | 不先做這個，下一輪會重問一次       |
| 二   | 六個無爭議修復（多數已在分支上） | 修法已存在，cherry-pick 比重寫便宜 |
| 三   | Badge 批次、報到桌寫卡（需決策） | 這兩項要先回答權限與裝置策略       |
| 四   | 場次報到                         | 前置問題是「你們的活動有場次嗎」   |

第一階段之所以排第一，是因為它改變的是「這件事以後要不要再花四小時問一次」。
它也是本輪唯一新增的程式碼，全部是檢查，不改產品行為。

## 7.9 需要你決定的五件事

前兩件沒有選項，只有是與否；後三件各是兩個選項，全文在 `04-gap-register.md`。

1. `audit/parity-20261022` 要合併還是丟棄？（它含 P0 修復，今天是活的）
2. 門口 OPERATOR 能不能封存／隱藏報名？（政策，不是技術）
3. 報到桌要不要在 App 上寫卡與上鎖？（決定後 G-8 才有意義）

**4. Badge 批次生命週期要不要上手機？（G-7，兩選項見 §G-7）**

- **A｜批次上手機**：建立批次、回填 UID、匯出都在 App。`M`，自成一個 sprint。
  驗收是「一場沒有 badge 資料的活動，全程在 App 上完成發卡」。選它等於承認
  「操作員會在手機上做批次作業」——六家產品都沒這樣做。
- **B｜單張在 App、批次留 Web**：增量主要是入口與文案（發卡走 `nfc-bind`，
  App 已有；後端的 `claim` 是發給展商，不是發給參加者），且能與第 3 項的報到桌
  寫卡併成一個 sprint。選它等於承認「批次是活動前準備工作」。

**5. 你們的活動模型有沒有場次？（G-9，兩選項見 §G-9）** 這一題不是優先度，
是事實：

- **有場次** → G-9 升 P1，排在 G-7／G-8 之後。前端 IA 是 `L`，但後端的名冊與
  場次報到端點**已經在了**，不必先排後端。
- **沒有場次** → G-9 移到 `BY_DESIGN`，並把「何時該重新考慮」寫進去。

維持 P2 待定等於默默選了「不做」，而且下一輪會再問一次同一個問題。

五個都有答案之後，`04-gap-register.md` 就沒有「待決策」這一欄了。

## 7.10 附：2026-10-29 的畫面觀察

你給的兩張截圖（App 的「NFC 寫卡」頁，跑在瀏覽器裡）對照出兩件事：

- **平台偵測是誠實的。** 畫面頂端寫「此瀏覽器不支援 NFC，請改用 Android 真機寫卡」，
  與程式碼的判斷一致（`LinkCard_Event_Admin_App_Expo@src/app/(auth)/[eventId]/nfc-bind.tsx:84`）。
  這不是缺陷，是正確的降級。
- **換卡／補發／退卡仍然是停用狀態**，橫幅寫「等待後端 WP-N2。作廢舊卡的端點尚未
  就緒」。我另外查過後端，`EventNfcController` 全檔沒有 replace／reissue／unlink／revoke，
  路由也只有 lookup／bind／exchange／badges／batch 這幾條。所以**停用是對的**，
  而且它把原因寫出來了。

這一項值得記在心裡：App 在「做不到」的地方是誠實的。這一輪找到的問題（死路由、
不存在的欄位）反而是「假裝做得到」的地方——那才是需要修的類型。

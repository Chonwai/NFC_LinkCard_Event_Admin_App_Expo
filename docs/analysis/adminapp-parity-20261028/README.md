## 會自己檢查自己的三個測試

這份報告最容易壞的地方是「引用漂移」——寫的時候指到某個檔案的某一行，之後
程式碼一改，那句話就變成假的。機械閘門只擋得住其中一半：**引用壞掉**（檔案被搬走、
行號超過檔長）會紅；**引用漂移**（檔案還在、行號也在範圍內，但那一行已經換成別的
東西）不會紅，只能靠人重讀。實例與行號證據見 `06-verification.md` §6.4 第 5 條。
這三條**不是同一件事**，差別在「需不需要 Web repo 在旁邊」：

| #   | 指令                        | 需要 `../LinkCard_Frontend` | 驗什麼                                                                                                                                                                                                                  |
| --- | --------------------------- | --------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | `npm run check:parity`      | 不需要                      | 登記表自身一致性、App 側檔案存在、P0/P1 缺口章節。Web 不在旁邊時頁面掃描**跳過**（印一行 `SKIPPED`，仍 `exit 0`）                                                                                                       |
| 2   | `npm run check:parity:full` | **需要**                    | 第 1 條的全部，加上「Web 有新頁面但沒有登記」。**射程只到「新增頁面」**：同一頁面長出新能力不在它的檢查範圍內（它比對頁面清單，不讀頁面內容）                                                                           |
| 3   | `npm test`                  | 不需要                      | 參照檢查＋登記表反例測試。**引用數不寫在這裡**：跑 `node --test tests/parity-citations.test.mjs`，它不論通過或失敗都會印一行 `MEASURED checked=… skipped=… ambiguous=… floor=… problems=…`；缺 sibling 時另印 `SKIPPED` |

上面三條的實作是：`tests/parity-citations.test.mjs`（每個 `Repo@path:line` 的檔案
存在、行號在範圍內）、`tests/parity-registry.test.mjs`（登記表本身的一致性，含反例
測試）、`scripts/check-parity-registry.mjs`（Web 頁面是否都登記了、P0/P1 缺口是否有
計畫章節）、`parity/parity-registry.json`（能力與缺口數的最終事實；引用時看檔案本身，`fa111a7`
時為 15 個能力、13 個缺口）。

CI 只跑第 1 條與第 3 條，而 CI 沒有 checkout Web repo——所以第 2 條在 CI 上
**不會發生**，只在你自己的機器上（或你手動跑）才會。

CI 另外還跑 `npm run check:contract`（契約閘門，不在上面三條裡）：它比對 App 的
15 條呼叫與後端路由快照，**不需要** Web repo。快照邊界與重算方式見
`06-verification.md` §6.6 第 5、9 列。

### 2. Web 這一週把報到桌做完了

`2649530 feat(checkin): write and bind the badge on the check-in screen` 之後，
Web 的 `/check-in/:eventId` 在報到成功後可以直接寫卡並綁定，並在寫入的同一趟把卡片
密碼設上去（取不到密碼就降級為不上鎖，不擋簽到）。App 的同一件事要跨兩個畫面、
斷一次連線，而且沒有上鎖能力（`src/utils/nfc-utils.ts` 全檔沒有 lock/pwd/protect
字樣）。

這一項在上一輪被記為「App 超集」，今天反過來了。

### 3. 兩邊的「不能做」都是硬體限制，不是偷懶

Web 寫卡需要 Web Bluetooth 與 ACR1555U 讀卡機，不支援的環境會顯示
`write-card-blocked`；掃碼報到仍然可用。App 寫卡需要 Android 的
`react-native-nfc-manager`，iOS 直接阻擋。所以「哪一邊是超集」取決於現場帶了什麼
設備，這一點在 `03-capability-matrix.md` §3.4 有完整對照。

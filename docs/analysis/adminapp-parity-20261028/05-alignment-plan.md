# 05 — 對齊計畫

這份計畫要解決的不是「App 缺幾個畫面」，而是「為什麼這個問題每兩個月要重問一次」。

上一輪（10-22）做了一份 4,300 行的審計，結論正確，然後停在未合併的分支上。
這一輪（10-28）重做了一次量測，才發現其中兩個判定已經過期。如果不改變產生
結論的方式，下一輪還會再發生一次。

所以計畫分兩層：先把「以後不必重問」的機制建起來（第一階段），再按缺口補功能
（第二、三階段）。

## 5.1 第一階段：讓這份結論可以被機器複驗（1 天）

| 動作                               | 解決什麼                                                    | 狀態                                                                |
| ---------------------------------- | ----------------------------------------------------------- | ------------------------------------------------------------------- |
| 提交 `parity/parity-registry.json` | 能力判定有唯一來源                                          | **已完成**（`parity/parity-registry.json` 在版控內）                |
| `npm run check:parity`             | **新增未登記的 Web 頁面**時會失敗——且只在 Web repo 在旁邊時 | **已完成**（CI 的 `Parity registry` step；射程限制見下）            |
| 把 `check:contract` 接進 CI        | 端點漂移會在 PR 上現形（G-11）                              | **已完成**（`.github/workflows/ci.yml` 的 `Backend contract` step） |

登記表回答的是「哪一個 Web 模組在 App 有對應、判定是什麼、證據在哪、理由是什麼」。
閘門做四件事：

1. 登記表裡每一個 `web.file` 與 `app.file` 都必須存在（檔案被搬走會被抓到）。
2. 每一個 `BY_DESIGN` 必須有 `rationale`，每一個 `APP_GAP` 必須有 `gapId` 與
   `severity`——沒有理由的判定不算判定。
3. Web 的 manage 模組清單若出現一個沒有登記的頁面，閘門失敗。
   這一條是整套機制的核心：**新增頁面會強迫做出判定**，而不是默默漂移。
   **但今天它不會在 CI 上執行**——見下方。
   另外要把射程說清楚：**本機制對「既有頁面長出新能力」無效**。它比對的是頁面清單，
   不讀頁面內容；一個早就登記過的頁面在裡面多做了一件事，閘門不會有任何反應。
   本輪 check-in 那一頁的判定失效正是這一類——頁面在清單裡，變的是頁面裡的東西，
   抓到它的是人的重測，不是閘門（實例見 `06-verification.md` §6.4 第 5 條）。
4. 登記表 `gaps[]` 裡每一筆 `P0`／`P1`，在 `04-gap-register.md` 都必須有一個
   `### <gapId>` 章節（`P2` 不強制）。方向是**登記表 → 文件**，不是反過來：
   `scripts/check-parity-registry.mjs` 的 `checkDocs()` 逐筆走 `registry.gaps`，
   用 `^###\s+<id>\s` 去比對 `04-gap-register.md`。所以「登記表自己漏列一個 P1」
   這一條抓不到——那是第 2 點（`APP_GAP` 必須有 `gapId`，且該 `gapId` 必須在
   `gaps` 清單內）與人的複核要負責的。

第 3 點值得多說一句。上一輪的 9 項「刻意差異」不是錯的，但它們是**當時**對照
**當時**的 Web 得出的。Web 這一週加了報到桌寫卡，沒有人回頭改那張表，
於是表格繼續宣稱「App 是超集」。

### 但這條規則今天在 CI 上不會執行

規則本身**有牙齒**（差分驗證過：假 Web root 放 18 個已登記頁 → `exit 0`；
再加 1 個未登記頁 → `exit 1`），但**今天的 CI 走的是跳過的那條路徑**：

- `package.json` 的 `check:parity` 是 `--web ../LinkCard_Frontend`，**沒有**
  `--require-web`
- `.github/workflows/ci.yml` 只有**一個** `actions/checkout@v4`，沒有 checkout
  `LinkCard_Frontend`
- 於是 `checkWeb()` 在 `existsSync(webRoot)` 為假時**直接 return**，只印一行
  `SKIPPED`，整個閘門以 `exit 0` 結束

換句話說：閘門在**開發者的機器上**（兩個 repo 並排）會抓，在 **CI 上**不抓。
所以「這種過期會變成紅燈」目前只對一半——它會變成你自己機器上的紅燈。

兩條路，代價不同，這裡不替任何人選：

**A. 讓 CI 真的掃到 Web。** 要 checkout 第二個 repo（需要 cross-repo 權限），
並把那一步改成 `npm run check:parity:full`。代價：CI 需要額外憑證；PR 會因為
**另一個 repo** 的改動而變紅，而改 PR 的人往往沒有那個 repo 的權限去修。

**B. 維持現狀，把完整掃描變成發版步驟。** 發版前手動跑
`npm run check:parity:full`，並在文件與 checklist 上明確標示「這是人工步驟，
不會自動擋」。代價：靠人記得，漏跑一次就回到今天的狀態。

## 5.2 第二階段：六個無爭議的修復（1 天）

### 這六項不必重寫，可以撿回來

**本段已完成，不需要再執行。** `1cb2b73` 以 merge 而非 cherry-pick 落地，因為同時
要帶入閘門與快照——cherry-pick 得逐個挑下面這 9 個 commit，而 merge 一次把分支上
的全部帶進來，也保留了「這些修法原本是同一條線」的歷史。下面的清單保留為歷史
紀錄與「哪些 commit 屬於這一組」的索引，不是待辦事項。

`audit/parity-20261022` 上已經有它們， cherry-pick 比重做便宜。**但不要只挑其中
幾個 commit**，因為那些修復彼此有依賴：

```
# 1) 契約閘門本體（含它的負向測試）
git cherry-pick 7c19f0a
# 2) 閘門漏收的 8 條巢狀 /import 路由 —— 少了這一步，閘門會誤報合法呼叫
git cherry-pick 421ab7c
# 3) 六個修復
git cherry-pick 5bcdb53   # G-1
git cherry-pick 9e3c7a2   # G-5
git cherry-pick 075f775   # G-3
git cherry-pick 031972f   # G-4a
git cherry-pick 84cb423   # G-4b
git cherry-pick 860404f   # G-2
git cherry-pick bc27abc   # G-2 的註解收尾
```

`421ab7c` 特別容易被跳過：它只是「補上 8 條路由」，但它決定了閘門以後會不會產生
假陽性。一個會說謊的閘門最後一定被忽略，所以它其實比任何一個 P1 都重要。

Cherry-pick 完跑一次 `npm run check:contract`，若仍報 `checkin/override`，表示
G-1 那一步沒進來；若報 `/import` 系列的路由不存在，表示 `421ab7c` 沒進來。

## 5.6 完成判準

這個計畫有兩個硬性完成條件，**兩個都要成立**：

1. **機械的**：`npm run check:parity` 與 `npm run check:contract` 都在
   **工作分支 `feat/nfc-gate1-reader-spike` 上綠，且已 push 讓 CI 真的跑過**，
   且登記表裡沒有任何 `APP_GAP` 處於「已判定但沒有 gapId」的狀態。

   > **這一條今天還沒滿足。** 兩支閘門在工作分支的 `HEAD` 上都是綠的（見下方
   > 實跑），但分支尚未 push（`git rev-list --count
origin/feat/nfc-gate1-reader-spike..HEAD` 不為 `0`），所以「已 push 讓 CI 跑
   > 過」這半句今天沒有任何證據。判準刻意寫成「綠 **且** 已 push」，就是為了
   > 不讓「我在本機跑過」冒充「CI 跑過」。

   兩支都在樹上，不再有待驗的那一半：`npm run check:contract` 在工作分支的
   `HEAD` 上可跑（`package.json:59`：`"check:contract": "node scripts/check-backend-contract.mjs"`），
   CI 也有這個 step（`.github/workflows/ci.yml:57` 的 `Backend contract`）。
   本節前版寫的「`check:contract` 還不是 `package.json` 的 script、只活在
   `audit/parity-20261022` 上」**已被推翻**——那個狀態在 `1cb2b73` 合併後結束。

   實跑（2026-10-29，App repo 根目錄）：

   ```
   npm run check:parity    # → ✓ 對等登記表一致：15 個能力、13 個缺口
   npm run check:contract  # → ✓ 15 條 App 呼叫全部對得上後端路由快照
   ```

   誠實邊界沒變：`check:contract` 比的是**快照**（後端 `64be09e`），不是活的後端；
   後端改路由要重跑 `--refresh`，否則它會驗一份過期的世界（見 `04 §G-11`）。

2. **決策的**：**P0／P1 的缺口沒有一個懸空。** 這一條問的是「有沒有人欠一個決定」，
   不是「有沒有做完」；判準用**允許清單**，只有三種 `status` 算已處置：
   `fixed`（已修，且修復 commit 已在本工作分支的 `HEAD` 上；驗證器要求 `fixedOn`
   非空）、
   `fixed-on-branch`（已修，但還停在分支上；驗證器同樣要求 `fixedOn` 非空）與
   `ready-to-implement`
   （已判定、非決策題、待實作；**與上面兩者一樣需要證據欄位**——驗證器
   要求 `decidedIn` 非空，值是一個可以回頭查的位置，例如
   `docs/analysis/adminapp-parity-20261028/04-gap-register.md#G-10`）。其餘任何值——
   `open`（沒人認領）、`decision-needed`
   （等人回答），以及日後新增的值——一律算懸空。用允許清單而不是排除清單，是為了讓
   新值預設落在「未處置」這一側，不會因為沒人更新判準就靜默變成「完成」。
   ** 「選 A、明確不做」是合格答案，但答案必須反映在登記表的 `status` 上。
   G-7（P1）是 `open`——它和當初促使這條判準改用允許清單的 G-0（P0，2026-10-29
   已由 `fixed` 結案）一樣，只看 `decision-needed` 的舊判準會在它懸空時回報
   「完成」。登記表目前用到五種值：`open`、`decision-needed`、`fixed`、
   `fixed-on-branch`、`ready-to-implement`（`scripts/check-parity-registry.mjs` 對
   `fixed`／`fixed-on-branch` 要求 `fixedOn` 非空、對 `ready-to-implement` 要求
   `decidedIn` 非空——不是只檢查欄位存不存在；新增值時驗證器要一起改，不能只寫在
   會議紀錄裡）。
   第四個值是為 G-10 加的：它是缺陷、`owner` 是 `none-needed`（無爭議）、但還沒修，
   用 `open` 會讓它長期被算成「等人認領」，而實際上沒有任何決定可做。
   第五個值 `fixed` 是為 G-1～G-5、G-11 加的：那些修復已於 2026-10-29 併入
   **本工作分支**（merge `1cb2b73`），因此在該分支的 `HEAD` 上可驗證。再用
   `fixed-on-branch` 會讓「在分支上」變成永久狀態，讀者無法從 `status` 分辨
   「已修且已在本工作分支 `HEAD` 上」與「還停在一條沒人合併的分支」。
   **`fixed` 的範圍只到工作分支**：`origin/main` 仍是 `7d0fcf5`；用詞定義見
   `04 §G-0`。
   `fixed` 與 `fixed-on-branch` 共用同一條證據要求（`fixedOn` 非空），差別只在
   可回溯性落在哪裡。

第 2 條可以重跑，不必憑印象（`exit 1` 表示還有未處置項，可以直接進 CI）：


原本把一件沒有爭議的事算成「懸空」的地方。

# 05 — 對齊計畫

這份計畫要解決的不是「App 缺幾個畫面」，而是「為什麼這個問題每兩個月要重問一次」。

上一輪（10-22）做了一份 4,300 行的審計，結論正確，然後停在未合併的分支上。
這一輪（10-28）重做了一次量測，才發現其中兩個判定已經過期。如果不改變產生
結論的方式，下一輪還會再發生一次。

所以計畫分兩層：先把「以後不必重問」的機制建起來（第一階段），再按缺口補功能
（第二、三階段）。

## 5.1 第一階段：讓這份結論可以被機器複驗（1 天）

| 動作                                    | 解決什麼                         |
| --------------------------------------- | -------------------------------- |
| 提交 `parity/parity-registry.json`      | 能力判定有唯一來源               |
| `npm run check:parity`                  | 判定過期時 CI 會失敗             |
| 把 `check:contract` 接進 CI             | 端點漂移會在 PR 上現形（G-11）   |

登記表回答的是「哪一個 Web 模組在 App 有對應、判定是什麼、證據在哪、理由是什麼」。
閘門做四件事：

1. 登記表裡每一個 `web.file` 與 `app.file` 都必須存在（檔案被搬走會被抓到）。
2. 每一個 `BY_DESIGN` 必須有 `rationale`，每一個 `APP_GAP` 必須有 `gapId` 與
   `severity`——沒有理由的判定不算判定。
3. Web 的 manage 模組清單若出現一個沒有登記的頁面，閘門失敗。
   這一條是整套機制的核心：**新增能力會強迫做出判定**，而不是默默漂移。
4. 登記表的 `register` 必須涵蓋 `04-gap-register.md` 裡所有 `P0`/`P1` 的 ID。

第 3 點值得多說一句。上一輪的 9 項「刻意差異」不是錯的，但它們是**當時**對照
**當時**的 Web 得出的。Web 這一週加了報到桌寫卡，沒有人回頭改那張表，
於是表格繼續宣稱「App 是超集」。登記表加閘門之後，這種過期會變成紅燈。

## 5.2 第二階段：六個無爭議的修復（1 天）

這六項不需要任何人做產品決定，且有五項已經在 `audit/parity-20261022` 上寫過一次。

| ID   | 動作                                       | 驗收                                              |
| ---- | ------------------------------------------ | ------------------------------------------------- |
| G-1  | 移除「申請主管覆核」與其 service 方法      | `check:contract` 綠；畫面上沒有會誤導的橫幅        |
| G-2  | Token 畫面移除死連結，或整頁移除           | 沒有指向 `/manage/:id/wallet` 的 URL              |
| G-3  | 錢包流水改讀真實欄位並加分頁               | 每行不再是 `—`；>20 筆可翻頁                      |
| G-4  | 補 `Registration` 欄位與兩個查詢參數       | 型別與後端投影一致；篩選送得出去且後端有反應      |
| G-5  | 以 `/my-access` 作為能力開關               | OPERATOR 看得到該看的、看不到不該看的             |
| G-10 | 總覽總數改用 `event.registrationCount`     | OPERATOR 不再 403；請求數下降                     |

順序建議：G-1 → G-10 → G-5 → G-3 → G-4 → G-2。
理由：G-1 與 G-10 直接影響現場，G-5 會改變其他頁面的顯示條件，所以排在資料層
修好之後但排在 UI 微調之前。

## 5.3 第三階段：兩個能力軌道（各 2–5 天，需決策）

### 軌道 A：Badge 生命週期（G-7）

範圍限在「現場需要什麼」：建立批次、回填 UID、匯出。不做批次認領（那是活動前
準備工作，Web 更合適）。

驗收：一場沒有 badge 資料的活動，可以全程在 App 上完成發卡，不需要開電腦。

### 軌道 B：報到桌寫卡（G-8）

先做決策再寫程式。三個決策點見 `04-gap-register.md` §G-8。

如果不做，替代方案是把 App 的定位說清楚：App 負責「沒有讀卡機時仍可報到」，
寫卡一律在有讀卡機的 Web 站進行。這也是一個有效答案，但必須寫進文件，
否則下一輪審計會再問一次相同的問題。

## 5.4 第四階段：場次報到（G-9）

排在最後的理由不是它不重要，而是它的前置是一個產品問題：你們的活動有場次嗎？
如果答案是有，這一項會變成 P1；如果沒有，它應該從登記表移到 `BY_DESIGN`。

## 5.5 不要做的事

| 不要做                                   | 為什麼                                                   |
| ---------------------------------------- | -------------------------------------------------------- |
| 把 Web 的 13 個模組逐一搬到 App          | 其中 8 個是設定／內容／財務工作，手機不是合適的裝置      |
| 在 App 重做一份授權判斷                  | G-5 的正解是問後端 `/my-access`，不是複製角色表          |
| 為了對齊而在 App 加一個 `/nfc` 診斷頁    | 那是維修工具，受眾是工程師，不是操作員                   |
| 為 `manage-stats` 而改 App 的總覽算法    | 它不修 OPERATOR 的 403；先做 G-10 的第一步                |
| 在文件裡寫死 commit 數或行數             | 上一輪為此改了兩次；寫下產生數字的命令                   |

## 5.6 完成判準

整個計畫只有一個硬性完成條件：

> `npm run check:parity` 與 `npm run check:contract` 都在 `main` 上綠，
> 且登記表裡沒有任何 `APP_GAP` 處於「已判定但沒有 gapId」的狀態。

這句話的意思不是「所有缺口都補完」，而是「所有缺口都有人認領或有人明確拒絕」。
前者是進度問題，後者是治理問題；只有後者會讓下一輪審計不必從零開始。

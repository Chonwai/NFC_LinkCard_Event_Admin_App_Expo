# 11 — 全面功能對齊：2026-10-29 的產品決定

<!-- citations: LinkCard_Event_Admin_App_Expo -->

**狀態：已決（2026-10-29）。** 本文記錄一個**推翻既有結論**的產品決定。它存在的理由
不是補完說明，是讓下一輪不必重新辯論同一件事，並且讓登記表不再說謊。

同一天稍早才寫下的 `03-capability-matrix.md:377`（§3.7）主張「依場景對齊、九個
`BY_DESIGN` 不進 App」。使用者在讀完之後**明確推翻它**。本文不捍衛 §3.7，而是：
①誠實記錄決定 ②界定「功能對齊」的可驗收定義 ③把 §3.7 仍然成立的代價轉成動工前的
問題（§3.7.8）。

## 11.1 決定（逐字引用使用者原話，不潤飾）

> 「手環的寫入是一次性的，不會重複用」
>
> 「其實可能有機會明明報了名，但係總算沒有，他當場保的話可能重新掃描多一次 QR code
> 去填報名表」
>
> 「是不是可以做完全對齊 Web 版本的功能？也就是說是不是可以完全根據網頁版
> LinkCard event admin portal 有的功能一模一樣，在這一個 Admin App 上去實現一次呢？
> 至少功能上面要統一對齊？儘管 UI 和 UX 可能有一點不一樣，但是我希望功能上要對齊！」

三句話是三件不同性質的事，強度不同，不可以混用：

| #   | 原話是什麼                | 性質                         | 它實際改變的東西                             |
| --- | ------------------------- | ---------------------------- | -------------------------------------------- |
| ①   | 手環寫入一次性、不重複用  | **事實陳述**（營運事實）     | 只影響 G-7 的**優先順序**，不影響做不做      |
| ②   | 報了名但系統沒有 ⇒ 重掃碼 | **情境補充**（會發生的例外） | 界定 G-6 的缺口範圍（見 §11.4）              |
| ③   | 功能要與 Web 全面對齊     | **決定**                     | 改變 9 筆 `BY_DESIGN` 的判定（§11.2、§11.3） |

①與②單獨看都不構成翻案的理由——它們是「現場長什麼樣」。真正推翻 §3.7 的是③，而③
是一個**目標函數的更換**，不是對事實的更正。

## 11.2 這個決定推翻了什麼

**被推翻的對象是 `03 §3.7` 的結論**，以及 `03-capability-matrix.md:319`（§3.6）九條
理由的**用途**：那九條原本用來「決定做不做」，現在只能「用來排先後」。

措辭紀律——這一節有兩件事要分開講，混在一起就會寫出錯的話：

**一、§3.7 的結論被取代，但它不是「錯的」。**

> §3.7 是在 **2026-10-29 被更高優先的產品一致性目標取代**。

它回答的問題是「App 該不該與 Web 一樣寬」。它給的答案（不該，App 應該窄而深）在
它的目標函數下是**站得住**的：判準（`03-capability-matrix.md:396` 的五個連乘條件）
沒有被任何新事實推翻，它列的代價也沒有消失（見 §11.5）。使用者換的是最佳化目標：
**一致性 > 窄而深**。兩個目標都合理，這是產品選擇，不是事實更正。所以本輪**不刪**
§3.7 的任何一行。

**二、但有一件事是真的錯了，而且必須承認：`BY_DESIGN` 被當成終點。**

`BY_DESIGN` 的語意是「設計上**決定不做**」，它的社會效果是「下一輪不必再問」
（驗證器甚至為此要求它必須帶 `decidedIn`，見 `scripts/check-parity-registry.mjs:165`）。
一旦決定要做，這 9 筆登記就從「判定」變成**假話**，而且是最糟的一種假話：它們會讓
下一個人以為這件事已經被想過、結論是不要做。

所以本輪的實質工作不是寫一篇論述，是**把那 9 筆的語意改回真話**（`APP_GAP`＝要做、
還沒做），同時**保留原本的 rationale**——理由本身是歷史，它證明了當時看到了什麼代價。
推翻它的是決定，不是證據。

## 11.3 「功能對齊」的操作型定義（本文最重要的部分）

「對齊功能」如果只寫成一句口號，就無法驗收，也無法拒絕任何東西——每個模組都可以
自稱「已經對齊了」。所以本節給出可判定的定義。

> **對每一個 Web 能力，App 必須能完成同一組狀態變更（create / read / update /
> delete / 狀態轉移），且呼叫同一個後端端點、產生同一組 DB 效果。UI 呈現方式可不同。**

拆成四個可逐項打勾的驗收條件：

| #   | 條件         | 怎麼判定（機械可驗）                                                 |
| --- | ------------ | -------------------------------------------------------------------- |
| A1  | 狀態變更集合 | 列出 Web 該模組能做的 mutation（增／刪／改／狀態轉移），App 一項不缺 |
| A2  | 端點相同     | 同 path、同 method；**不接受**「等效的新端點」                       |
| A3  | DB 效果相同  | 被寫入的欄位／列與 Web 一致（含稽核欄位、時間戳、操作者）            |
| A4  | 可達性       | 從 App 導覽能走到，不是藏在深處的路由                                |

**明確不列入驗收**（否則「對齊」會變成無限大）：

- **UI／UX、版面、字級、互動手感**——使用者原話已明說「UI 和 UX 可能有一點不一樣」。
- **i18n 字串的逐字相同**——語意相同即可。
- **效能的絕對值**——只要求同一支端點，不要求同一條查詢計劃。

**明確排除（不在對齊範圍）**：

1. **`nfc-diagnostic-tool` 維持 `WEB_ONLY_INTERNAL`。** 查證後的理由不是假設：那頁
   自己寫明是「ACR1555U 讀卡機的現場診斷工具」、描述為「NFC 讀卡機的**內部診斷
   頁面（不對外開放）**」，並以 `noindex` 雙重阻擋
   （`LinkCard_Frontend@app/nfc/page.tsx:8`、`:14`、`:19`）；它需要 **Web Bluetooth** 接
   實體讀卡機，而且**不在 admin portal 的模組導覽內**（它是 `/nfc`，不是
   `/manage/:eventId/*`）。⇒ 它不是「Web 後台的一個功能」，是工程師的診斷台。
   **使用者不需要它在 App**；若日後要在手機上診斷讀卡機，那是新的**硬體能力**需求
   （App 已有 `nfc-read`），不是對齊。
2. **App 獨有的畫面不在對齊範圍。** registry 的 `appOnly` 現有 3 項：`walk-in`
   （現場報名）、`nfc-exchange`（卡片交換）、`nfc-read`（手機感應讀 UID）。它們是
   硬體能力或 Web 本來就沒有的入口，**Web 沒有可對齊的對象**。
   （派發說明寫「4 個畫面」並列出 `nfc-bind`／`token`，與 registry 不符，見 §11.7。）
3. **G-13（換卡／補發／退卡）不在本決定範圍。** 它不是「Web 有、App 沒有」，是
   **兩邊都缺後端端點**（`docs/analysis/adminapp-parity-20261028/04-gap-register.md:968`），
   維持 `deferred`。對齊只處理單邊落後的情形。

### 11.3.1 逐模組實作標的

**為什麼要這一節。** 上面 A1–A4 是可判定的驗收定義，但它們是**格式**，不是**內容**：
八筆能力在 `parity/parity-registry.json` 的 `rationale` 開頭逐字相同、`decidedIn` 全指
向 `#11.3`，所以只讀登記表的人只知道「要做」，不知道**在 App 上要能做什麼**。這一節
把每個模組的標的寫成一句「App 要能完成的狀態變更」。

**來源不是重新發明。** 每一句都是從
`12-parity-build-plan-20261029.md` §12.2.3 的「需新建什麼」欄萃取，並對齊同表的
「後端端點」欄。若兩份文件哪天不一致，以 `12 §12.2.3` 為準（它才是逐模組的工項清單）。

| #   | 模組             | App 要能完成的狀態變更（一句話）                                                         | 承接缺口 |
| --- | ---------------- | ---------------------------------------------------------------------------------------- | -------- |
| 1   | `profile`        | 在 App 上修改活動的名稱、時間、地點與狀態／落地頁模式，並送出同一支 `updateEvent`。      | G-15a    |
| 2   | `content`        | 對落地頁的 section 與 card 做增、改、刪（8 條端點裡實際用到的 6 條），不只是看。         | G-15a    |
| 3   | `settings`       | 修改活動的收款帳戶資料與主題色並儲存——不是 App 現有那頁「登入者偏好」。                  | G-15a    |
| 4   | `exhibitors`     | 把廠商狀態由「待審」改成通過或退回，並完成一次 CSV 匯入（含逐列錯誤檢視）。              | G-15b    |
| 5   | `ticket-types`   | 新增／修改／刪除票種、切換 capability 開關，且改完的 `formFieldsJson` 通過語意綁定驗證。 | G-15b    |
| 6   | `polls`          | 建立投票、啟用它、關閉它，並讀到計票結果。                                               | G-15b    |
| 7   | `bank-transfers` | 把一筆匯款由「待核」改成「已核」或退回，且按下之前有第二次確認。                         | G-15c    |
| 8   | `org-roles`      | 邀請一個人成為活動管理員、並把既有管理員移除——即授予與收回後台權限。                     | G-15c    |

**`sessions` 不在上表。** 它走 `04 §G-9`（同一個產品決定，但後端只缺 1 條 `DELETE`，
見 `12 §12.3` 的 `ESC-CRA-001`）；它的標的與上表同構，記在 `§G-9` 以免同一句話寫兩份。

**這張表不改變 A1–A4。** 它是 A1（狀態變更集合）的具體化，不是替代品：驗收仍然要
逐項列出 mutation 並確認 App 一項不缺。

## 11.4 兩個新答案如何改變 G-6 / G-7

### G-7（Badge 批次生命週期）——「手環一次性寫入」讓它也變得不重要，但不是不做

使用者原話：「手環的寫入是一次性的，不會重複用」。這直接削弱批次生命週期的**現場**
價值：如果同一條手環不會被重複寫入、也不會回收再發，那麼「批次作廢／換發／重用」
這一整組操作在現場幾乎不會發生。

但**對齊的要求還在**，所以記法必須分成兩句，缺一句就會寫錯：

- **功能仍要做**（`badges` 已是 `APP_GAP`／G-7，見
  `docs/analysis/adminapp-parity-20261028/04-gap-register.md:471`）——Web 有這個能力，
  對齊就要有。
- **現場優先級最低**，可以排最後一波：它是 9 個新目標裡唯一被營運事實直接降權的。

> ⚠️ **不要寫成「不用做」。** 使用者要的是功能對齊；「一次性」是排優先順序的依據，
> 不是排除的依據。

**這是本輪新增的事實，不是既有文件的更正。** 上一輪為止，「一次性寫入」在全份分析
文件裡 **0 次**出現（`grep -n '一次性\|不重複' ` 只命中文不相關處）。它現在是 G-7
排程的最低依據，寫在這裡是為了讓它不必再被口頭傳承。

### G-6（名單管理）——缺口是「管理既有報名」，不是「不能現場報名」

使用者原話：「明明報了名，但係總算沒有，他當場保的話可能重新掃描多一次 QR code 去
填報名表」。這個情境說的是：**報名資料與現場不一致時，現場要能當場補登**。

而這件事 App 已經在做：`src/app/(auth)/[eventId]/walk-in.tsx`（304 行）就是現場報名頁
（`LinkCard_Event_Admin_App_Expo@src/app/(auth)/[eventId]/walk-in.tsx:1`），
`03-capability-matrix.md:390` 也把它當成「App 扛得住重表單」的證據。所以正確的說法是：

- **App 能現場報名**（`walk-in`，`appOnly` 之一；Web 沒有這個入口）。
- **G-6 的缺口是「對既有報名做管理動作」**：隱藏／封存／登記退款／更正狀態／匯出，
  App 是 0（`docs/analysis/adminapp-parity-20261028/04-gap-register.md:386` 起）。

**與派發前提的差異（照實記錄，修正留給後續 commit）：**
`04 §G-6` 全節 **0 次**提到 `walk-in`（`grep -c 'walk-in' 04-gap-register.md` → `0`）。
它的首句「App 只能查」在**範圍上**是對的（該節談的是管理動作），但它從不說明
「現場報名已經存在」，於是容易被人讀成「App 在名單這一塊什麼都不能做」。這不是一句
錯話，是一個**缺一句話的對**。本輪不改 `04` 正文（Commit 2 只加橫幅），差異記在此處。

### 附帶：`sessions` 也被改判，與同日稍早的結論相反

同一天稍早的 `10-session-decision-20261029.md` 記下「你們沒有場次」，並把 G-9 移到
`BY_DESIGN`、寫成「這一項永遠不做」
（`LinkCard_Event_Admin_App_Expo@docs/analysis/adminapp-parity-20261028/10-session-decision-20261029.md:18`）。
全面對齊把它一起改判：Web 有 `/sessions`（含名冊子頁），依 §11.3 的 A2，App 就得有。

兩者不矛盾，但只有這樣理解才不矛盾：

- **「沒有場次」是營運事實，它沒有變**，所以這個功能對現場幾乎沒有價值。
- **「要不要做」由一致性目標決定**，不由使用價值單獨決定。

⇒ `sessions` 是 9 個新目標裡**價值最低、但實作最便宜**的一項：後端（名冊、出席標記、
409 併發保護、專測併發的單元測試）已經完成，缺的只有 UI（見 `10` §10.3）。它的
`status` 因此從 `by-design` 改為 `ready-to-implement`（不是 `by-design`——同一個
「不做」不可能同時成立）。

## 11.5 已知風險（不因決定而消失）

這三項在 §3.7.5（`03-capability-matrix.md:456`）已經寫過，決定**沒有**讓它們消失，
只是改變了它們的身分：從「所以不要做」變成**動工前必須一併處理的前置條件**。

| #   | 風險     | 為什麼在「全面對齊」下更嚴重                                                | 現況       |
| --- | -------- | --------------------------------------------------------------------------- | ---------- |
| 一  | 誤觸     | 同一個 app 內同時有「掃碼發手帶」與「改票種／核匯款」，趕時間誤入即實際後果 | 設計不存在 |
| 二  | 權限     | 「手機上的 OPERATOR 能做多少事」沒有任何一層定義過                          | 設計不存在 |
| 三  | 發版節奏 | 後台功能進 App 後，小改動＝一次建置／審核                                   | 未評估     |

逐項的具體問題與逐項現況在 `03-capability-matrix.md` §3.7.8——那一節是本表展開後的
版本，狀態欄以它為準。三項**全部 `OPEN`**：沒有一項是「順手補一下」能答的，把它們算進
工期的人要先知道這一點。

## 11.6 這個決定**沒有**改變的東西（避免過度推論）

- 3 個既有 `APP_GAP`（Badges／Registrations／Check-in）不因此降級或升級。
- `severity` 一個都沒改（派發要求）。本輪只動 `verdict`：`BY_DESIGN → APP_GAP`。
- `nfc-diagnostic-tool` 仍是 `WEB_ONLY_INTERNAL`；`G-13` 仍是 `deferred`。
- 沒有動 `src/`。這是文件與登記表的決定記錄，不是實作。
- §3.7 的判準仍然可以用來**排順序**（它答的是「哪個比較急」），只是不再用來
  **決定做不做**。

## 11.7 與派發前提不符的四件事（誠實回報）

寫這些不是為了糾正誰，是因為**照著錯誤的前提做事會產生假的完成**。

1. **`04-gap-register.md` 內 `walk-in` 命中 0 次。** 派發說「先確認現有描述是否已
   正確」——真相不是「描述不正確」，是**根本沒有這段描述**。詳見 §11.4。
2. **`appOnly` 是 3 項，不是 4 項。** 派發列出 `nfc-bind`／`nfc-exchange`／`nfc-read`
   ／`token`；registry 的 `appOnly` 實際是 `walk-in`／`nfc-exchange`／`nfc-read`。
   （`token` 是 G-2 修過的 App 畫面，`nfc-bind` 是 G-8 流程的一部分，兩者都不在
   `appOnly`。）同一個清單若被寫成 4 項，日後會有人去找兩項不存在的東西。
3. **`tests/parity-registry.test.mjs` 沒有硬編碼 `BY_DESIGN === 9`。** 它只有一條測試
   用 `BY_DESIGN` 驗「沒有 rationale 要失敗」（`tests/parity-registry.test.mjs:173`），
   不涉及數量。所以「不要改成 `=== 0`」這條指令**沒有適用對象**；真正要處理的是
   `03 §3.1` 的統計行（`03-capability-matrix.md:28`、`:31`）與
   `07-briefing.md:79` 那張表——它們是同一事實的副本，不改就會與 registry 分岔。
4. **`status`／`decidedIn` 在現行 schema 屬於 `gaps[]`，不屬於 `capabilities[]`；**
   而驗證器要求**每一個 `APP_GAP` 都必須有存在的 `gapId`**
   （`scripts/check-parity-registry.mjs:118`）。九筆改判後若沒有對應缺口，閘門會
   直接紅。處理方式見 Commit 2（需要一個承接「全面對齊」的缺口條目）。
